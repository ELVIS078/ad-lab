# Detection — T1558.003 Kerberoasting

## Deploying the rule

```bash
docker cp wazuh-rule.xml <manager-container>:/var/ossec/etc/rules/local_t1558_003.xml
docker exec <manager-container> /var/ossec/bin/wazuh-control restart
```

**Before deploying**: run `execute.sh` once first, then in the Wazuh
dashboard search for the resulting `4769` event and note the actual
parent rule ID your ruleset assigned it (Security events → filter
`rule.id` is a 6xxxx decoder match on EventID 4769). Swap that ID into
`<if_sid>` in `wazuh-rule.xml` — this is intentionally not pre-filled
with a guessed number (see comment in the XML).

## Validating it

1. Set creds and run the attack:
   ```bash
   export DOMAIN_USER=attacker-user DOMAIN_PASS='AttackerPass123'
   ./execute.sh
   ```
2. In the Wazuh dashboard: **Security events**, filter `rule.description`
   contains `Kerberoasting`. You should see a level-10 alert naming
   `svc-sql` within a few seconds of the TGS request.
3. Cross-check the raw event: `win.eventdata.TicketEncryptionType` =
   `0x17`, `win.eventdata.ServiceName` = `svc-sql`.
4. Screenshot, redact, save to `../evidence/`.

## Query reference (KQL — Microsoft Sentinel/Defender)

```kql
SecurityEvent
| where EventID == 4769
| where TicketEncryptionType == "0x17"
| where ServiceName !endswith "$"
| project TimeGenerated, Account, ServiceName, Computer, IpAddress
```

## Query reference (SPL — Splunk)

```spl
index=wineventlog EventCode=4769 TicketEncryptionType="0x17"
| where NOT match(ServiceName, "\$$")
| table _time, Account_Name, Service_Name, Client_Address
```

## Baseline note

In a real environment, some legacy apps still force RC4 — run this
query for a week against production *before* setting the rule to a
high severity, and allowlist known-legitimate RC4 services by name
rather than disabling the rule outright. In this lab, `svc-sql` is the
only RC4 service account, so there's no baselining needed.
